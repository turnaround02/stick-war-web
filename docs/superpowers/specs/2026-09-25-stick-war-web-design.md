## 1. 意图与成功标准

### 1.1 意图

在浏览器中实现一个机制上致敬《火柴人战争：遗产》的**单机 2D 即时战略游戏**：玩家经营金矿、征募火柴人军队、在一条横向战线上与敌方 AI 交战，目标是摧毁敌方基地。

游戏为**纯静态站点**，无后端、无账号、无联网对战。美术与音效全部程序化生成，不依赖任何外部素材，因而不涉及第三方版权资产。

### 1.2 成功标准

| 编号 | 标准 | 判定方式 |
|---|---|---|
| S1 | 核心闭环成立：挖金 → 造兵 → 推进 → 摧毁敌方基地 | 手动完成关卡 2 一局 |
| S2 | 兵种相克可被玩家感知 | 相同造价的不同编成对撞，胜负符合 §6.5 的克制关系 |
| S3 | 桌面浏览器帧率稳定 | 在**实测峰值负载（约 25 单位）**下 ≥ 58fps。**勘误（M5）**：原文写「同屏 120 单位」，但实测峰值只有 23~25 单位；120 只是「双方人口上限 60+60」的**理论天花板**，从未被接近。该标准原本在测一个**不存在的场景**，已改为按实测负载表述 |
| S4 | 战斗结果可复现 | 相同种子 + 相同指令序列 → 逐 tick 完全相同的世界状态 |
| S5 | 数值可快速迭代 | headless harness 跑完一场完整对局 < 500ms |
| S6 | 单局时长符合预期 | 关卡 2 为 **3~6 分钟**（实测 276 秒，见 §8.4.3）；无尽模式首次战败在**实测区间**内（见 §8.4.4，spec 原写的 12~15 波已被实测推翻） |
| S7 | 部署可用 | 推送 `main` 后 GitHub Pages 自动构建并可正常游玩 |

### 1.3 非目标（明确排除）

- 多人对战、联网、后端服务、账号系统
- 移动端触屏适配（仅做输入层抽象，不做真机适配）
- 科技树、法术、英雄单位、装备系统
- 存档云同步
- 背景音乐（音效做，BGM 不做）

## 3. 架构

### 3.1 核心决策：确定性逻辑核心与渲染层分离

这是全项目最重要的架构决策。游戏被切成两半：

- **`src/sim/`** —— 纯 TypeScript 世界状态与规则。不 import 任何渲染库。以固定 30Hz 的整数 tick 步进，输入是「上一帧状态 + 本帧指令」，输出是「新状态」。完全可单测、可在 Node 里无头高速运行。
- **`src/render/`** —— Phaser 场景。每渲染帧读取 sim 的状态快照，绘制火柴人、HUD、相机。**从不写回 sim 状态**。

驱动这一决策的三个理由：

1. **平衡迭代**：兵种数值平衡需要跑成千上万次快速对局。分离后可在 Vitest 里以 1000 倍速无渲染跑完整场战斗。
2. **确定性回放**：战斗手感调试需要「同一输入必得同一结果」。耦合渲染的架构做不到。
3. **避免幽灵 bug**：杜绝「改了渲染代码导致 AI 行为变了」这类问题。

代价是初期多一层状态同步，约多 1 天工作量。

**模块边界规则：**

- `data/` 只含常量与类型，可被 `sim/` 与 `render/` 同时引用。
- `sim/` 可引用 `data/`，**不可**引用 `render/`、`input/`、`i18n/`。
- `render/` 与 `input/` 可引用 `sim/` 的类型与只读状态，**不可**修改 sim 状态。
- `input/` 产出 `Command` 对象（纯数据），由 `render/` 每帧交给 `sim.tick()`。
- 单元测试位于各模块旁的 `*.test.ts`。

**依赖方向严格单向：`sim/` → `data/`。** 共享的数据域类型（`UnitTypeId`、`ArmorType`、`Side`、`MatchConfig`、`WaveScript`）定义在 `data/` 下，`data/` 不 import `sim/`。

**`Command` 类型定义在 `sim/types.ts` 而非 `input/`。** 这是边界规则的直接推论：`sim/` 不能 import `input/`，所以 `sim` 必须消费的类型不能住在 `input/`。`input/` 只提供构造 `Command` 的辅助函数。

ESLint 规则（`eslint.config.js`）强制第一条边界：

```js
{
  files: ['src/sim/**/*.ts'],
  rules: {
    'no-restricted-imports': ['error', {
      patterns: ['phaser', '**/render/**', '**/input/**', '**/i18n/**'],
    }],
  },
}
```

### 3.3 逻辑帧与渲染解耦

```ts
// render/scenes/BattleScene.ts 的 update 骨架
const STEP_MS = 1000 / 30;
accumulator += delta;

while (accumulator >= STEP_MS) {
  const commands = input.drainCommands();      // 本逻辑帧的指令
  step(world, commands);                       // 推进一个 tick
  accumulator -= STEP_MS;
}

const alpha = accumulator / STEP_MS;           // 插值系数
renderWorld(world, alpha);
```

- 逻辑固定 30Hz，渲染每帧用 `alpha` 在 `unit.prevX` 与 `unit.x` 之间线性插值。插值**只作用于渲染用的位置与肢体角度**，不影响逻辑。
- 每单位多存一份 `prevX`（一个 number）即可。
- 30Hz 对这类游戏足够：单位速度 70~95 px/s，一个逻辑帧移动 2.3~3.2 px，配合插值无可见抖动。

## 4. 世界状态模型

### 4.1 类型骨架

以下为接口签名（完整实现由 plan 给出）。

type UnitTypeId = 'miner' | 'swordsman' | 'archer' | 'spearman';

### 4.2 指令模型

```ts
type Command =
  | { kind: 'train';     side: Side; typeId: UnitTypeId }
  | { kind: 'setStance'; side: Side; unitIds: number[]; stance: Stance };
```

单轴战场下不提供「点地面移动」。单位控制采用**姿态制**：`advance`（推进）/ `hold`（驻守原地）/ `retreat`（撤向己方基地）。全局「全军推进 / 全军撤退」按钮通过 `setStance` 传入全部己方单位 id 实现，共用同一条代码路径。

单位被选中（`selected`）是纯渲染状态，**不进入 sim**。

## 5. 时间与确定性

### 5.1 整数 tick 铁律

数据表用**秒**（浮点）书写，因为那是人类调数值时的自然单位；加载时一次性转换为**整数 tick**：

```ts
const TICKS_PER_SEC = 30;
const toTicks = (seconds: number) => Math.round(seconds * TICKS_PER_SEC);
```

运行时所有计时器（冷却、前摇、采集、造兵、眩晕）**必须是整数 tick**。原因：浮点累积误差会破坏确定性，导致同一份种子在两次运行中分叉，使 §9.2 的回放与批量模拟失效。

位置可以保持浮点——只要运算顺序固定，IEEE754 是确定性的。移动速度在加载时预计算为 `speedPerTick = pxPerSec / 30`。

### 5.2 随机性

sim 内**禁止**任何非确定性来源。需要随机时（无尽模式波次构成、AI 决策抖动）使用 `sim/rng.ts` 的种子 PRNG（mulberry32），其状态 `rngState` 随 `World` 一起序列化与回放。

## 6. 战斗模拟

### 6.1 单个 tick 的更新顺序

`sim/tick.ts` 严格按以下六步执行，**顺序固定且不可调换**：

1. **经济** —— 矿工采集进度、金币入账、人口核算、造兵队列推进
2. **指令** —— 消费本 tick 累积的 `Command[]`；`economy` 模式下 AI 战术层在此产出指令
3. **AI** —— 单位层目标选择与状态迁移
4. **运动** —— 按状态更新期望位置；随后执行 1D 排序-分离约束
5. **战斗** —— 前摇计时推进 → 结算伤害 → 标记死亡
6. **清理** —— 移除死亡单位与命中弹丸、处理基地血量与胜负判定

两个关键约束及其理由：

- **运动必须先于战斗**：否则伤害判定使用的是上一 tick 的位置，射程边界会出现一 tick 的系统性误差。
- **伤害结算必须先于清理**：否则本 tick 被标记死亡的单位仍会打出一击，产生「尸体补刀」。

顺序一旦变更，同一份种子输入将产出不同结果，§3.1 架构的全部收益立刻失效。因此本顺序是**回归测试的断言对象**。

### 6.2 单轴移动与分离约束

战场退化为一条 X 轴（§7.2 说明了相机模型），不使用 Phaser 的物理引擎。分离约束是自写的确定性算法：

1. 按阵营分组，各组内按 `x` 升序排序。**比较器必须是全序**：`x` 相同时以 `unit.id` 决胜，不得依赖 `Array.prototype.sort` 的稳定性。
2. 同阵营相邻单位维持最小间距 `minGap = a.bodyRadius + b.bodyRadius`；若小于该值则沿 X 反向推开。
3. 敌方单位之间**不可穿透**：当两敌对单位的间距 ≤ 双方半径之和时，双方停止前进（进入接触）。
4. 远程单位的额外约束：当自身与目标距离 ≤ `attackRange` 时停止前进，不再逼近。

**推挤的让位权重**（决定谁被推开）。优先级从高到低，高优先级单位让位更少：

| 让位权重 | 条件 | 含义 |
|---|---|---|
| **0（完全不让）** | 基地 | 不可移动的圆形障碍，`bodyRadius = 40` |
| **0.25** | `stance === 'retreat'` | 撤退单位必须能穿过自己的战线，否则 `retreat` 完全失效 |
| **0.5** | `state === 'gather'` 或 `state === 'stunned'` | 采集/眩晕中的单位无法自主避让 |
| **1.0** | `state === 'attack'` | 攻击中的单位有「重量感」，但仍可被推开 |
| **1.5** | 其余（`idle` / `move`） | 空闲单位最容易被挤开 |

推开量按双方权重**正比**分配：权重 `w` 的单位让出的比例为 `w / (self + other)`。

> 注意方向：权重是「让位的多少」，**不是**「优先级」。权重 `0` 的单位让出 `0 / (0 + other) = 0`，即完全不让 —— 这正是基地不可移动的含义。权重 `1.5` 的空闲单位让出 `1.5 / (1.5 + 0.25) ≈ 86%`，而撤退单位只让出约 14%，于是撤退单位能把自己人推开、穿过战线。两边让出的比例之和恒为 1，重叠被完全解开。

> **为什么 `attack` 不是完全不可推：** 若攻击中的单位变成不可移动的钉子，密集阵型会形成「僵尸墙」，后排永远挤不进去，R2 的纵深设计失效。
>
> **为什么 `retreat` 权重最高：** 撤退方向是朝己方基地，而友军正挡在身后。若不给它最高让位权重，撤退单位会被自己人卡死，`retreat` 形同虚设，而 §6.3 的「挥砍可被躲开」与 §6.4 的「边退边打」都依赖它。代价是撤退时会出现一阵推挤，这是 1D 约束的固有代价且仅限撤退时发生。

**执行顺序**（`movementSystem` 内部，固定不可换）：

```
1. 记录 prevX
2. 按状态/姿态积分期望位置
3. 同阵营分离   —— 正向扫一趟（向右推）+ 反向扫一趟（向左推）
4. 敌对阻挡     —— 放在分离之后，因为分离可能把单位推进敌人身体里
5. 钳制到 [0, worldWidth]
```

两趟扫描是必要的：单趟从左到右无法解开链条（A 推 B，B 推 C，但 C 的位移没传回 B）。两趟足以解开链条，且趟数固定因而确定性。

复杂度 O(n log n)，完全可单测，是本架构最受益于纯逻辑核心的部分。

**位置钳制**：所有单位 X 被钳制在 `[0, worldWidth]`，防止被推挤挤出地图。

### 6.3 单位状态机

状态集：`idle` / `move` / `gather` / `attack` / `stunned` / `dead`。

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| `idle` | 初始；无目标且无需移动 | 选定目标 → `move`/`attack`；收到姿态指令 → `move` |
| `move` | 有目标但距离 > 交战距离；或姿态指令要求位移 | 进入攻击距离 → `attack`；抵达驻守/撤退点 → `idle` |
| `gather` | 矿工抵达金矿（M3） | 采集 tick 用尽 → `move`（携带金币返回基地） |
| `attack` | 与目标距离 ≤ `attackRange` | 目标死亡/脱离锁定 → `idle`；目标移出射程 → `move`；前摇完成并出手 → 留在 `attack` 等冷却 |
| `stunned` | 受眩晕效果影响（v1 无来源，预留） | `stunTicksLeft` 归零 → `idle` |
| `dead` | `hp <= 0` | 本 tick 步骤 6 移除 |

`stunned` 在 v1 没有任何技能会产生它，但**必须预留在状态枚举与 tick 逻辑中**——它是后续所有控制类效果（击退、眩晕、恐惧）的挂载点，提前留出槽位的成本为零。

**近战与远程的差异**不单列状态，而是 `attack` 状态内部的两个阶段：

- **近战**：`attack` 时停下不动，前摇 → 伤害直接作用于目标。
- **远程**：`attack` 时停下不动，前摇 → 生成一枚 `Projectile`，其 `ticksToImpact = round(distance / projectileSpeed * 30)`，到达时结算伤害。目标提前死亡则弹丸消失。

**前摇的三条硬规则**（M2 裁决，全部服务于「微操拉怪」这个核心手感）：

1. **前摇一旦开始必须走完**，不可被打断、不可重开。目标中途死亡也照常挥空。
   - 若允许取消前摇，混战中单位会因目标频繁切换而无限重开前摇，永远打不出伤害。
2. **出手瞬间重新检查射程**。目标已移出射程或已死亡 → **挥空**（不造成伤害），直接进入冷却。
   - 这是让「后撤躲挥砍」有意义的机制。若无条件命中，撤退就毫无价值。
3. **出手瞬间不切换目标**。若目标已不存在，挥空后回到 `idle` 重新选目标。
   - 若自动转向最近的敌人，伤害会凭空改变方向，视觉上无法解释。

**`retreat` 姿态下的行为**：退向己方基地，停在**基地的战场侧前沿**（`base.x + dir × (BASE_RADIUS + r)`）。
途中**若敌人进入射程仍然还击，但不停下**（边退边打）。这使撤退成为一个有代价的战术选择，而不是无敌逃跑键。

> **M3 修正**：M2 的 `integrateRetreat` 用的是 `base.x − dir × (BASE_RADIUS + r)`，即退到基地**后方**（玩家停在 246）。
> M2 时这个值被走廊钳制覆盖（实际停在 354）所以没暴露；矿点移到基地战场侧后，退到后方会让撤退单位与往返的矿工争空间。
> 撤退的语义是「退到安全处重新集结」，而基地前沿正是防线所在，所以改成 `+`。

### 6.3.1 矿工采集循环（M3）

矿工是唯一进入 `gather` 状态的兵种。完整循环：

```
carrying = 0  →  target = {kind:'mine', side}     →  move（赴矿）
到达矿点      →  gather（90 tick，即 3s）          →  goldLeft -= 载重
采集完成      →  carrying = 载重，target = {kind:'base', 己方}  →  move（返基地）
抵达基地前沿  →  金币 += carrying，carrying = 0      →  target = {kind:'mine'}  →  move（赴矿）
```

**方向由 `target` 唯一表达**：「回家」就是**矄准自己的基地**。这样 `movementSystem` 无需任何矿工特判
（只需给 `targetX` 加一个 mine 分支），且矿工遇敌时能自然切换到敌对目标。

「矄准自己基地」是安全的 —— §6.3 的 `isAllyTarget` 守卫已保证单位不会攻击己方基地。

**两个时机必须分开**：
- `goldLeft -= 载重` 在 **`gather` 完成时**（矿脉真的少了）
- `金币 += carrying` 在 **抵达基地时**（金子真的运到了）

所以「矿脉枯竭」与「矿工死在路上」是两个独立的经济损失。

**矿脉枯竭**：`goldLeft` 不足一次载重时采集剩余量；归零后矿工转入 `idle`（停在原地待命，可被姿态指令调动）。
这是一个**有意义的终局信号** —— 玩家看到矿工停下就知道经济结束了。

**矿工的优先级**（`aiSystem` 内，与其他兵种不同）：

| 优先级 | 条件 | 行为 |
|---|---|---|
| 1 | 有敌在 `TARGET_ACQUIRE_RANGE` 内且姿态是 `retreat` | 逃向己方基地，丢弃当前挖矿任务 |
| 2 | 有敌在范围内且姿态不是 `retreat` | **继续挖矿**（矿工 `attack = 0`，切到战斗状态只会站着挨打） |
| 3 | 无敌 | 执行挖矿循环 |

即：**无敌时姿态无效，有敌时姿态生效**。矿工唯一的自保手段是 `retreat`。

### 6.3.2 造兵队列（M3）

`World.trainingQueue` 是**每方一个串行队列**，无长度上限，**不可取消**。

| 事件 | 效果 |
|---|---|
| 收到 `train` 指令 | 检查金币足够 **且** `popUsed + 队列未出生数 + 本次 ≤ popCap`；满足则**立即扣金**、入队 |
| 队列头 `ticksLeft` 归零 | 单位在基地前沿外侧出生，**出生时才占人口** |

**为什么无上限是安全的**：金币是硬约束（没金排不了队），人口上限是第二道闸。

**为什么不可取消**：取消退款是一个完整的小功能（需记下单时价格、处理已部分训练的情况），
属于打磨而非核心闭环。

**为什么人口在下单时就检查**：若等到出生时才查，人口满会导致「金币已扣但单位不出生」或
「队列头卡住不动」—— 后者最糟，界面显示「训练中」但永远不动，玩家无法理解。
前置到下单意味着限制体现在**可见的按钮状态**（变灰 + 提示「人口已满」）。

**出生位置**：基地前沿外侧依次排开（第 1 个在 `baseFront + 60`，之后每个 +`bodyRadius×2`）；
若该位置已被占（间距不足）则继续外推直到找到空位。全部在同一点出生会让新单位与既有单位深度重叠，
分离约束虽然会解开，但会产生一次剧烈的「爆开」推挤，且可能把单位推过基地前沿导致阵型混乱。

### 6.3.3 指令的消费时机（M3）

速度控制（§7.2）会让一帧跑多个 tick，所以必须定义指令归属哪个 tick：

```ts
const ticks = timestep.advance(delta * speed);
for (let i = 0; i < ticks; i++) {
  step(world, i === 0 ? input.drainCommands() : []);
}
```

**指令只进入本帧的第一个 tick，之后清空。** 语义是「本帧收到的指令，在下一个逻辑 tick 生效」。

若进入每一个 tick，「造兵」指令在 4x 速度下会被重复下单 4 次，直接吃掉玩家四倍的金币。

**这也是为什么 `step` 接受 `commands` 数组而不是自己读输入队列**：把「何时消费」的决定权留在调用方。

### 6.4 目标选择与仇恨

**搜索规则：**

- 单位在**前方** `TARGET_ACQUIRE_RANGE = 500px` 内（含自身两侧 `targetTolerance = 20px` 的容差）搜索**最近**的敌对目标。
- 一旦选定即**锁定**，直到目标死亡、或距离超过 `LOCK_BREAK_RANGE = 700px`。只有空闲（`idle`）时才重新搜索。
- 「前方优先」而非「全向就近」：避免后线单位转身去追击从背后溜过的敌方矿工，同时自然形成两军对撞的推进感。

**为什么用一对全局常量而不是 `attackRange * 2.5`：** 后者代入数值后弓箭手得 500px（恰好等于获取距离，无迟滞 → 边界处疯狂重选目标），剑士得 75px（小到「追一个后撤的敌人跑 75px 就放弃」）。`500 / 700` 给出明确的迟滞带，且让 `attackRange` 只管射程，语义不再混杂。

**目标可以是敌方基地。** 用判别联合表达：

```ts
type TargetRef =
  | { kind: 'unit'; id: number }
  | { kind: 'base'; side: Side }
  | { kind: 'mine'; side: Side }   // M3：矿工的导航目标
  | null;
```

判别联合让类型系统强制处理所有情况，`switch` 时不会遗漏。哨兵 id（负数）会在序列化和调试时坑人；把基地建成 `Unit` 则会让「基地」污染所有单位逻辑（它有 `stance` 吗？有 `cooldown` 吗？）。

**`{kind:'mine'}` 的引入（M3）**：矿工需要「去矿点」这个导航目标，而它既不是单位也不是可攻击的基地。
用 `TargetRef` 表达让「单位想去哪里」始终由**一个字段**决定，`movementSystem` 无需为矿工写特殊分支。
若改用单独的 `minePhase` 字段，就会造出第二套导航机制，与 `target` 并行且可能矛盾
（`minePhase = toMine` 但 `target = 某个敌人`，听谁的？）。

**没有敌方单位时的行为**（按姿态区分）：

| 姿态 | 无敌军时的行为 |
|---|---|
| `advance` | 推进至射程内，攻打敌方基地 |
| `hold` | 原地待命；**若敌方基地已进入射程则打**（守住阵地但顺手拆塔） |
| `retreat` | 退向己方基地，不主动攻击基地 |

> `hold` 语义是「原地不动，但敌人送上门就打」。若 `hold` 永不攻击基地，驻守会变成消极挨打；若所有姿态都自动拆塔，撤退就失去意义。

**派生规则 R1 —— 弹丸穿过友军。** 远程单位发射的 `Projectile` 只检测敌方单位，友军单位不阻挡弹丸，友军也不阻挡友军的视线判定。

**R1 的理由：** §6.5 的核心设计是「弓箭手必须被前排掩护才能输出」。若弹丸会被己方单位拦截，则弓箭手站在剑士身后时将完全无法命中任何目标，该设计直接崩溃。因此 R1 不是可选优化，而是让远程兵种可用的**必要条件**。

**派生规则 R2 —— 交战不阻断后排。** 前排单位与敌人接触（互相停止前进）时，后排单位可继续前进到其自身被前排的 `minGap` 约束为止，即后排会自然地「贴上来」形成纵深队列，而不会因为前排停下而全体停住。

**R2 的理由：** 若采用「前排停下则整队停下」的规则，120 单位规模下战线会退化成单排，弓箭手永远暴露在最前方，§6.5 的阵型深度设计同样崩溃。R2 由 §6.2 的分离约束天然实现——约束只作用于相邻单位对，不传播。

**R2 的理由：** 若采用「前排停下则整队停下」的规则，120 单位规模下战线会退化成单排，弓箭手永远暴露在最前方，§6.5 的阵型深度设计同样崩溃。R2 由 §6.2 的分离约束天然实现——约束只作用于相邻单位对，不传播。

### 6.5 伤害与护甲模型

```
mult  = target.armorType in attacker.bonusVs ? attacker.bonusVs[target.armorType] : 1
raw   = attacker.attack * mult
dmg   = max(raw - target.armor, raw * 0.1)        // 10% 保底伤害
```

- **减法护甲**天然产生「高护甲单位免疫低级兵海」的效果，这是原版里「巨人踩死一群剑士」的观感来源。
- **10% 保底**避免出现「完全打不动」的死局。
- **克制乘算**作用在护甲之前，提供一条与护甲正交的、可独立调节的平衡旋钮。

**重要设计修正：** 朴素的三方相克（剑士>弓箭手>矛兵>剑士）在 1v1 下**不成立**。推演可知：弓箭手需约 13.5 秒才能杀死一个剑士，而剑士只需约 2 秒就能贴脸。弓箭手 1v1 打不过任何近战。因此实际模型为：

| 关系 | 依据 |
|---|---|
| **矛兵 > 剑士** | 对重甲 ×1.6 加成 + 射程 45 vs 30 的先手优势 |
| **剑士 > 弓箭手** | 移动更快（95 vs 75）+ 对轻甲 ×1.5 加成，约 4 秒内贴脸 |
| **弓箭手 > 一切无近战掩护的目标** | 射程 200，但**必须**有前排挡住敌人才有输出空间 |

也就是说，弓箭手的价值不体现在 1v1，而体现在**有掩护时的输出效率**。这反过来强制玩家构建有纵深的阵型——这正是原版最好玩的地方，也是 R1/R2 必须成立的原因。

### 6.6 死亡与胜负

- `hp <= 0` 的单位在本 tick 步骤 5 被标记 `state = 'dead'`，在步骤 6 从 `units` 数组移除。**标记与移除必须分属两步**，否则步骤 5 的遍历会在中途改变数组长度。
- **死亡动画不进 sim。** sim 立即移除死亡单位；渲染层在 `syncStickmen` 的 diff 中发现单位消失时，用**死亡时的位置与调色板**创建一个脱离 sim 的临时精灵，播完 0.4s 动画后自毁。这样既保住了两阶段死亡不变量，又满足 §11 的「死亡动画」要求；且死亡动画是纯表现，本就不该让 sim 为它承担状态复杂度。
- **胜负判定两个条件**（`cleanupSystem` 内）：
  1. 任一方基地 HP ≤ 0 → 对应胜负。
  2. **某一方单位数归零 → 该方判负。** 这条是为了让无基地的 harness 对撞场景也能得出明确结论，否则矩阵表格会充斥「超时」行而失去意义。
- 双方基地同时归零（理论可能）判为 `playerLose`。
- `outcome !== 'ongoing'` 后不再推进 tick。

### 6.7 伤害统计

`World` 携带 `stats: Record<Side, { damageDealt: number }>`，由 `combatSystem` 累加，随世界一起序列化。

这是 §9.3 harness 输出「双方总伤害」的数据来源。不用「对比战斗前后的 HP 总量反推」是因为：它无法区分「造成 300 伤害」与「造成 300 伤害但对方回复了 300」（M5 可能加回复），也会漏掉打在基地上的过量伤害。

## 7. 表现层

### 7.1 程序化火柴人渲染

每个单位对应一个 Phaser `Container`，内含持久化的 Shape 子对象（头、躯干、上臂/前臂 ×2、大腿/小腿 ×2、武器）。动画通过按关键帧插值各肢体的 `rotation` 实现。

**为什么不用另两种方案：**

- **每帧 Graphics 重绘**：实现最直白，但 120 单位 × 每帧清空重画会使 GPU 调用爆炸。
- **启动时预烘焙纹理图集**：性能最好，但内存占用大、动画帧数受限、生成逻辑复杂，且与「骨骼角度可自由插值」的平滑度相冲突。

骨骼容器的优势：肢体是**持久对象**，只改旋转，无每帧分配；动画平滑（角度连续插值而非帧跳）；天然支持「换武器/换配色即新兵种」。

渲染层只消费「当前状态 + 状态进入 tick」即可推导动画进度：

```ts
const stateAge = world.tick - unit.stateEnteredTick;
const phase = stateAge / stateDuration(unit.state);   // 0..1
```

武器与配色由 `render/stickman/palette.ts` 按 `typeId` 决定，新增兵种无需新增美术资源。

**朝向不进 sim。** 单轴战场上「玩家在左、敌人在右」是恒定事实，朝向由 `side` 推导（玩家单位朝右，敌方朝左）。加 `facing` 字段到 `Unit` 换不来任何玩法差异，等将来有「背刺」类机制再升级。

#### 动画关键帧

每个状态是一组关键帧，`poseFor` 在相邻关键帧之间做**线性插值**：

```ts
interface Keyframe { atPhase: number; pose: Pose; }
const POSE_KEYFRAMES: Record<UnitState, Keyframe[]>;
```

| 状态 | 帧数 | 循环 | 说明 |
|---|---|---|---|
| `idle` | 2 | **循环** | 轻微呼吸起伏 |
| `move` | 4 | **循环** | 双腿交替，`phase` 由 `tick % cycleTicks` 推导 |
| `attack` | 3 | **一次性** | 举刀 → 挥下 → 收势 |
| `gather` | 3 | **循环** | 挥锄（M3） |
| `stunned` | 1 | — | 单帧（预留） |
| `dead` | 1 | — | 单帧；真正的死亡动画在渲染层的幽灵精灵上 |

**关键约束：`attack` 的「刀刃接触帧」必须落在 `phase = windupTicks / totalTicks` 处。** 这是 `windupTime` 字段存在的全部意义 —— 攻击动画的接触帧必须与伤害结算 tick **精确对齐**，否则打击感全失。

用关键帧数组而非正弦函数程序化生成的理由：「举刀 → 挥下」这种非对称动作用正弦表达很别扭，而且无法让接触帧精确落在指定 phase。

### 7.2 相机与战场

**矿点位置的修订（M3）**：矿点原本在基地**后方**（x=50 / 2950），但 M2 的基地走廊把单位钳制在
`[354, 2646]` 内，矿工永远走不到 x=50，采集循环无法启动。把矿点移到基地的**战场侧**
（x=550 / 2450）同时解决三件事：矿工能到达；敌方无需穿过基地就能威胁矿工（保住 §8.3
「敌方可以拦截矿工」的意图）；基地保持「墙」的语义。代价是往返距离从 310px 降到 190px，
单矿工产出从约 2.0 升到约 2.4 金/秒。

1.0x 时视口约 1280px，可见约 43% 战场；0.6x 时约 2133px（接近全局），可纵览战线；1.2x 时可看清单个单位的挥砍动画。缩放是「全局观察 ↔ 局部微操」的切换开关，是该玩法可玩性的核心来源。

**相机 X 钳制**：相机 X 必须钳制在 `[0, worldWidth − viewportWidth/zoom]`。0.6x 时视野宽 2133px，相机只能在 `[0, 867]` 内滚动，否则会露出世界外的空白。

**速度控制**：1x / 2x / 4x，**只改变每帧跑几个 tick，不改变 tick 本身的逻辑**。实现为 `FixedTimestep.advance(delta × speed)`，30Hz 逻辑帧率不变，累加器上限仍生效。速度是**纯渲染层的时间缩放**，`world` 完全不知道速度存在 —— 因此同一份种子在任何速度下产出相同结果（这条必须有测试）。

### 7.3 HUD

HUD 全部用 **Phaser GameObject** 实现（`Text` + `Graphics` + `setInteractive()` 的 `Rectangle`），元素设 `setScrollFactor(0)` 固定在屏幕上。不用 DOM 覆盖层：那会引入两套坐标系（DOM 像素 vs 世界像素）与两套事件系统，窗口缩放时的同步是持续的 bug 来源。

| 区域 | 内容 | 锚定方式 |
|---|---|---|
| 左上 | 金币、人口（已用/上限）、训练进度条 | `(16, 16)` |
| 右上 | 菜单、暂停、速度控制（1x / 2x / 4x） | 锚定右上角（右对齐）；**M8 修订**：菜单键在最左，返回关卡菜单 |
| 底部 | 命令栏：六个兵种按钮、全军推进/驻守/撤退 | 锚定底部，按视口宽居中 |
| 顶部 | 战线指示器：双方基地血条 + 单位位置分布直方图 | 顶部居中，宽为视口 40% |

**锚定边缘而非绝对坐标** —— 否则窗口一变宽，右上角的元素就跑到屏幕中间。复用 `BattleScene.layout()`（M1 建立，窗口缩放时重算）。

**右上按钮簇是点击守卫的一部分**（M8 修订）：守卫的右上保留区从**按钮簇的实际布局**推导（菜单键的左缘），不再硬编码 240px——菜单键把簇的左缘推到 1280 宽下的 x=948，硬编码守卫会让「点菜单键」穿透成「选中 900px 外的单位」。布局链每加一个按钮，守卫自动跟着变宽。

**对局中返回菜单需确认**（M8 修订）：HUD 菜单键弹「返回菜单？进行中的对局将丢失」确认浮层（确认/取消），**不做**免确认直达——误触代价是整局进度（本项目不存进行中对局，§10.1.1）。确认浮层显示期间对局冻结（等效暂停），空格键不穿透。

**选中状态属于渲染层，不进 sim**（§3.1）。选中集是 `BattleScene` 的一个 `Set<number>`；姿态指令作用于选中的单位，「全军」按钮传所有己方单位 id。

**选中反馈用脚下椭圆标记，不用 tint** —— 兵种区分完全依赖配色（§7.1 的 `palette.ts`，且风险清单第 7 条明确说「0.6x 下靠配色+武器形状区分」），加 tint 会破坏这个唯一的信息通道。

底部命令栏在桌面与未来移动端都更顺手（拇指区）。战线指示器是「单轴 + 滚动相机」玩法的**信息补偿**——相机滚动时玩家看不到全局，该指示器是唯一的全局态势来源。

**选中方式：** 点击单个单位选中它（再点空白取消），**不做框选**（单轴战场上框选意义不大）。多选留到 M5。

#### 7.3.1 战线指示器（M5b 落定）

抽成 `render/frontline/layout.ts`（纯函数）+ `render/frontline/index.ts`（薄渲染器，与 `hud`/`result` 同形）。分桶是纯算术，正是「肉眼看着对、边界错一位」的东西，**必须有单测**。

- **直方图只统计战斗单位，不统计矿工。** 矿工在基地与矿点之间往返会形成两座**静态凸起**，把「单位分布」的真实信号淹没——矿工不是战线信息。
- **24 个桶**（世界约 3000px ≈ 每桶 125px）。桶边界按 `floor((x - minX) / bucketWidth)` 计算，越界归入首/末桶。
- **顶部居中，宽为视口 40%**（原文保留），两端接双方基地血条。
- **必须扩展 `handleClick` 的点击守卫**：指示器在视口顶部居中，而 `handleClick` 目前的守卫只保留左右各 240px，**顶部中央会被点击穿透**。新增「顶部中央保留区」守卫，防止点指示器误选单位。

### 7.4 音频

v1 使用 **WebAudio 程序化合成音效**，零素材、零版权风险，与 §8.1 的程序化美术策略一致。

音效清单：挥砍、命中、死亡、金币入账、造兵完成、基地受损。

打击感的构成中音效占比不低于动画。§6.3 中 `windupTicksLeft` 之所以关键，正因为它同时是「画面刀刃接触」与「音效播放」的同步点。**背景音乐不做**（对玩法验证无贡献）。

> **平衡修订（M3 后，首次 harness 迭代）**
>
> §8.2 的推演声称「剑士克制弓箭手成立」，但那是 **1v1** 的结论。首次跑完整对撞矩阵时，**弓箭手严格占优**：9 个判别场景里只有 4 个符合 §6.5 的意图 —— 弓箭手无掩护也能打赢剑士与矛兵，且它更便宜（80 vs 100/90）、训练更快（7s vs 8s/7s）。
>
> 两处改动修好了它（改动后 9/9 场景在 6 个种子上全部一致）：
>
> 1. **弓箭手 `maxHp` 80 → 70**。80 时弓箭手挨剑士 3 击才死，70 时 2 击即死 —— 这**只惩罚无掩护的弓箭手**（有掩护的靠前排挡刀，输出时间不变），正是 §6.5 想惩罚的行为。实测掩护伤害倍率因此从 2.45 升到 **3.39**。
>    - **刻意避开 65 与 45**：两者恰好落在伤害断点上（`ceil(65/32.5)`、`ceil(45/24)`），胜负会取决于「多挨一击」，任何其他改动都会让它漂移。70 是唯一不在断点上的取值。
> 2. **矛兵补上 `light ×1.5`**。原先矛兵只有反重甲加成，导致「十个矛兵打不过十个弓箭手」，这是全游戏**唯一**违反 §6.5「弓箭手 1v1 打不过**任何**近战」的地方 —— 属于**机制缺失**，不是数值松紧。
>    - **1.5 是实测下限**：1.4 与 1.45 仍会让十个弓箭手赢九个矛兵。
>    - 与剑士的反轻甲同为 ×1.5，看似模糊了分工，实则不然：剑士反轻甲 DPS 为 `25×1.5/1.0 = 37.5/s`，矛兵为 `24×1.5/1.2 = 30/s`，「剑士才是轻甲杀手」依然成立。
>
> **排查过程中被推翻的假设**（记录以免重复走弯路）：
> - **「射程 200 让弓箭手白拿齐射」不成立**：射程降到 180 **完全无变化**，160 也几乎无变化（仍胜），要到 140 才翻转；且降射程会**破坏**有掩护场景（弓箭手靠射程越过前排射击，射程一降就打不到）。
> - **「加造价」无效**：对撞 harness 不消耗金币，造价只影响场景标签，不改变任何结果。
>
> 这套判别已固化为 `src/sim/counter-relations.test.ts`（10 个场景 × 6 种子，必须全体一致）。此前 `harness.test.ts` 只 `console.table` 打印矩阵、断言「不抛异常」，所以弓箭手严格占优时测试套件依然是绿的 —— 平衡是 spec 要求，不是待汇报的趣闻。

### 8.2 单位对决推演（TTK 矩阵）

`hits = ceil(hp / dmg)`，`TTK = windup + (hits - 1) * cooldown`。

| 攻击方 ↓ / 目标 → | 矿工 | 剑士 | 弓箭手 | 矛兵 | 基地 |
|---|---|---|---|---|---|
| **剑士** | 1.25s | 7.25s | **1.25s** | 6.25s | 199.3s |
| **弓箭手** | 3.90s | 13.50s | 4.50s | 11.10s | 449.1s |
| **矛兵** | 2.70s | **5.10s** | 3.90s\* | 5.10s | 126.3s |

\* 矛兵对弓箭手另需 1.82s 接近时间（155px @ 85px/s），实际 5.72s。

**结论与验证：**

- 矛兵杀剑士 5.10s < 剑士杀矛兵 6.25s → **矛兵克制剑士成立**，且矛兵射程 45 > 30，先手命中（矛兵 0.30s 出手，剑士需先补 15px 位移，0.41s 才出手）。
- 剑士杀弓箭手 **1.25s**（弓箭手 70 HP，剑士对轻甲 37.5 伤害 → 2 击），弓箭手杀剑士 13.50s → **剑士克制弓箭手成立**。考虑接近时间，剑士实际约 4.04s 内解决弓箭手，期间承受约 2 箭（36 伤害，约占自身 24%）——**克制明显但不碾压**，这是期望的手感。
- 矛兵对弓箭手：`ceil(70 / 36) = 2` 击 → 2.70s，加接近时间约 4.52s。低于弓箭手杀矛兵的 11.10s，**矛兵 > 弓箭手成立**。
- 弓箭手杀剑士 13.50s，剑士 DPS 对基地 15/s，单个剑士拆 3000HP 基地需 199s，10 个剑士 20s。

> **注**：本表是 **1v1** 推演，只用于看兵种相克的**方向**。真正决定平衡的是 §9.3 的整编对撞矩阵 —— 1v1 的「剑士克制弓箭手成立」在**整编**下曾经不成立（弓箭手严格占优），详见 §8.1 的平衡修订。

> **修订（M4a，实测）**：上表「单矿工产出」与下面那段「12 个矿工 → 28.8 金/秒」是**按矿工互不干扰推演的，实测不成立**。M4a 用 12 矿工跑关卡 1 时发现：**1 矿工 2.33 金/秒（符合），12 矿工 0.22 金/秒，随后彻底停摆**。原因是战场只有一条轴、矿点在基地与前线之间，矿工**必然双向通行**，而一维世界里对向单位无法互相穿过 —— 出去的和回来的正好互相推回，净位移为零，运金车永远到不了入账点，第一趟载重就是最后一趟。

> **实测（稳态，预热 10s，取 60s 窗口）：**
>
> | 矿工数 | 1 | 3 | 4 | 6 | 8 | 12 |
> |---|---|---|---|---|---|---|
> | 金/秒 | 2.33 | 6.00 | 8.00 | 10.67 | 14.67 | **19.33** |
>
> 人均效率随人数下降（单车道拥堵），所以**12 矿工约 19 金/秒**才是可实现的数，不是 28.8。调经济 AI 请按此表，不要按旧推演。

**推演（按上表实测值重算）：** 开局 200 金，造 2 矿工（100 金）还是 2 剑士（200 金）是一个真实的取舍。12 个矿工 → 约 **19.3 金/秒** → 每约 **5.2 秒**产出一个剑士。全局金币总量 6000 ≈ 最多 60 个剑士，与人口上限 60 形成双重约束。

**注意（已知隐患，M4b 已实测确认并处理）：** 矛兵对基地的 DPS/金币 原估为 `(24×1.6−10)/1.2/90 ≈ 0.263`，剑士为 `15/100 = 0.150`，矛兵效率高出 75%。**M4b 实测（10 单位围攻 3000 HP 基地）确认了这个隐患：**

| 编成 | 拆完 3000 HP 用时 | 备注 |
|---|---|---|
| 10 剑士 | 70.0 s | — |
| 10 矛兵 | **45.1 s** | 比剑士快 **1.55×** |
| 10 弓箭手 | **永不** | **缺陷，见下** |

按**每金币**折算，矛兵约比剑士高效 **1.7×** —— 与原估的 +75% 一致，只是这次是实测而非公式。注意这不是「单兵 DPS」而是**编队吞吐**：走廊钳制让同一时刻只有前排 2~3 个单位进入基地射程，所以数字远低于 `攻击/冷却` 的理论值。

**已确认的缺陷（M2 遗留，M4b 修复）：** `combat.ts` 的 `spawnProjectile` 只处理 `target.kind === 'unit'`，对基地目标**静默返回**。于是**远程单位对基地造成零伤害**，且无任何报错 —— 弓箭手会永远站在射程内循环挥弓。近战路径（`applyDamage`）处理 `kind:'base'`，所以这是**远程路径漏了一种目标类型**。M2 修过「近战打不到基地」（`distanceToTarget` 量到基地圆心），但**远程打基地从未被测过**。修法与验证见 §13.7 Q7。

### 8.4 关卡、波次与胜利条件

#### 8.4.1 胜利条件（M4b 修订）

**背景（实测）。** §6.6 原本有两条胜利条件：基地归零 **或** 某方单位归零。在**对称经济关**里后者**总是先发生** —— 实测 30 局，双方基地**全部保持满血 3000/3000**，一局都没有被碰过。于是「摧毁敌方基地」（游戏前提）**从不决定胜负**，基地沦为装饰品；而且胜负在「某一刻对方单位归零」时即判，对局被压缩到 169 秒（§8.4 原定目标 5~8 分钟）。

更根本的是：经济关的敌方**会重建**，「单位归零」在语义上根本不是终局。

**修订。** `MatchConfig` 新增 `winCondition: 'annihilation' | 'base'`（默认 `'annihilation'`，保持既有行为）：

| 值 | 语义 | 用途 |
|---|---|---|
| `'annihilation'` | 基地归零 **或** 敌方单位归零即判胜；玩家单位归零判负 | 关卡 1（脚本波，敌方无经济，无可重建） |
| `'base'` | **只有基地归零才判胜**；敌方单位归零只是「可以安心拆基地了」。玩家单位归零**仍立刻判负**（不给翻盘幻觉） | 关卡 2（对称经济关） |

**为什么不从 `enemyAi` 推导。** `enemyAi` 是「敌方有没有经济」，`winCondition` 是「怎么算赢」——两者恰好在本作的两关上重合，但把两个概念绑在一起是**巧合耦合**：以后想做「有经济但只需歼灭」的模式（如无尽）就会打架。显式字段还让两关的差异**在数据里一眼可见**。

**不会卡死（实测）。** 双方金矿储量有限（各 6000），最坏情况是资源耗尽后由尚存军队的一方推平基地。实测基地条件下对局在 **243~252 秒**结束，**无僵局**。验收另加一条「有限步内必然终止」的单测（§13.7 Q15）。

#### 8.4.2 关卡 1（教学关）

敌方基地 HP 1500，敌方**无经济**，纯脚本波次，`winCondition: 'annihilation'`：

| 时刻 | 敌方兵力 |
|---|---|
| t = 5s | 2 剑士 |
| t = 50s | 3 剑士 + 1 弓箭手 |
| t = 110s | 4 剑士 + 2 弓箭手 + 1 矛兵 |
| t = 180s | 8 单位混合编成（4 剑士 + 2 弓箭手 + 2 矛兵） |

关卡 1 无经济是**有意设计**：它把玩家的注意力从「管经济」引向「管战线」，是最省成本的引导手段。它也是**唯一**使用 `'annihilation'` 的关卡 —— 敌方兵力全在波次表里，清完就是真的清完。

#### 8.4.3 关卡 2（对称经济关）

敌方拥有完整经济（1 金矿、3 起始矿工、200 起始金）、人口上限 60、启用 §9.1 的两层 AI，**无波次**，`winCondition: 'base'`。

**敌方基地 HP：1500**（与关卡 1 的敌方基地一致）。理由是**实测驱动的**：基地 HP 3000 时，突破敌方军队后还有约 43 秒**无抵抗**的磨基地时间（敌方军队与经济同时死亡，实测结束时敌方单位 0、金币 0、矿工 0）。降到 1500 把这段压缩到约 22 秒。关卡 1 的敌方基地本来就是 1500，**有先例**。

**实测时长（最终发布配置，5 个种子完全一致）：**

| 项 | 值 |
|---|---|
| 时长 | **276 秒 = 4.6 分钟** |
| 结束方式 | 敌方基地 1500→0（玩家基地满血） |
| 敌方档案 | `LEVEL_2_ENEMY`：`minerTarget 8` / `decisionIntervalTicks 30` |

> **数值修订记录。** 本节早先写的是 243~252 秒，那是**两次错误扫描**的结果（第一次在测试循环里同时驱动双方，命令顺序与 sim 不同；第二次 spread 了 `PLAYER_REFERENCE`，于是扫的是一个**不存在的档案**）。两次都被「有一条测试钉死时长」发现。正确的做法是**在即将发布的那个档案基础上**只改要扫的旋钮。完整表格见 `src/sim/ai-profile.ts` 的注释。

**目标时长（修订）：** 关卡 2 单局 **3~6 分钟**。原写 5~8 分钟是**在「基地参与战斗」的假设下推演的，而当时的胜利条件让基地根本不参与** —— 与 §8.3 的经济勘误同源。实测 276 秒在新区间内，故采纳实测而非硬凑数值。

#### 8.4.4 无尽模式（M5）

**波次节奏：** 每 25 秒一波。第 N 波（1-based）到点 tick = `750 × N`。

**难度靠预算，不靠乘算。** 第 N 波金币预算 `100 + 60N`，换算成单位后由波次表免费提供。**不使用**原设计的「难度系数 `min(1 + 0.03N, 2.0)` 乘算作用于 HP 与攻击」：

> **勘误（M5，实测驱动）。** 原设计用乘算系数，实测后**删除**该机制，理由有三：
> 1. **预算单独就足以产生不可避免的战败。** 实测（用 spec 参数代理跑）：`100+60N` 下玩家在第 8 波战败；更陡的 `100+150N` 下第 4 波。根因是**结构性**的 —— 敌方兵力**免费**，玩家为每个替补付费且收入固定（6 矿工 ≈ 10.7 金/秒），所以玩家军队卡在 ~10 个单位不动，敌方单调增长。乘算系数是**多余的旋钮**。
> 2. **它从未被实现。** `MatchConfig.difficultyMult` / `World.difficultyMult` 是死字段（拷进 `World`，无任何 system 读取，也不在 `hashWorld` 里）。既然不用，就**删除**而不是留着继续当陷阱（§15 登记表已记录此义务）。
> 3. **删它避免给 `Unit` 新增字段。** 乘算需要把系数快照到每个单位上（否则已在场的老单位也会跟着变强，语义错误），而 `Unit` 新增字段**必须改 `hashWorld` 的 unit 行** —— 本项目已两次漏过哈希覆盖。少动一次就少一次风险。

**目标波次：** 原写「首次战败在第 12~15 波」**已被实测推翻**（实测第 8 波，且那还没算上原设计的乘算系数）。该数字是**推演值**，必须以实测为准 —— 与 §8.3 的经济勘误、§8.4.3 的时长勘误同源。**发布值由 M5a 的扫描确定并写进代码注释**，验收区间**从实测反推**。

**构成规则：** 固定比例 + **随波号渐进引入新兵种**（前几波只有剑士，之后依次加入弓箭手、矛兵），而非纯随机加权。理由：①纯随机会让「第 N 波」这类验收点**不可复现**，而可复现是本项目的核心纪律；②渐进引入让难度爬升的形状可被玩家感知。

**不用 PRNG。** `sim/rng.ts` 已存在但**从未被任何 system 消费**（实测：所有关卡对种子完全惰性）。无尽波次生成**本可以**成为第一个消费者，但固定构成规则已足够，**能不用随机就不用** —— 这与 §5.1「确定性优先」的取向一致。若将来确实需要抖动，生成必须把新 `rngState` 写回 `world` 且结果必须进哈希。

**终局：** 无尽模式**只能战败**（`endless: true` 时「敌方单位归零」永不判胜，见 §6.6），因此它属于 `'annihilation'` 一侧 —— 不靠清场获胜。玩家侧「单位归零即负」**无条件保持**。**明确接受**：无尽里敌方不会攻击玩家基地（`targeting` 单位优先），因为无尽的目标是「撑多少波」而不是「拆基地」。

**入口：** 无尽模式作为 `LEVELS` 的**最后一项**，战役打完关卡 2 后由结果浮层的「下一关」进入。

**HUD 与结算：** 无尽模式在 HUD 显示**当前波次**（「第几波」就是它的分数），结果浮层显示**撑到第 N 波**与 localStorage 里的**历史最高波次**。战役关显示「关卡名 · 用时」，无尽关显示波次 —— 两者由纯函数模块分支（`hud/layout.ts`、`result/layout.ts`），可单测。

**结果浮层的按钮按关卡类型区分**（M5 修订）：战役关 = 「重玩」+「下一关」（末关时为「返回第一关」）；无尽关 = 「重玩」+「返回第一关」（**没有下一关**）。

#### 8.4.4b 关卡 3（M6.1，M7c 人口修订，M10 敌方军备修订）

对称经济关：3000/3000 基地、双方 **300 起始金 + 5 矿工**、`winCondition: 'base'`、敌方档案 `LEVEL_3_ENEMY`（`minerTarget 7` / `decisionIntervalTicks 30`，buildOrder `['miner','swordsman','archer','giant','mage']`）。

**人口上限 12（M7c 修订，实测驱动）。** 原值 8 的问题：`minerTarget 7 + 1 战斗位` 意味着双方 **30 秒内即满 8/8 且全程满员**，buildOrder 的其余兵种没有展开空间，玩家金币在中后期积压 ~2790 无处可花。扫描（5 种子、`runMatch` 真实路径、只改 popCap）：

| popCap | 时长（5 种子全胜+拆基地） | 与窗口中心 270s 的距离 |
|---|---|---|
| 8（基线） | 281s | +11s |
| **12** | **280s** | **+10s，正中** |
| 16 | 213s | −57s |
| 24 | 212s | −58s（与 16 等效） |

选 **12**：校准几乎零扰动（280 ≈ 281），同时解锁「双巨人（6 人口）+ 真实经济」的结构。16/24 的实测表明 16 之后节奏被「敌方早期崩溃」饱和，额外人口不再改变对局形状——若将来想要更宽松的手感，重钉 213s 即可（一行）。

**敌方经济强化 + buildOrder 加入巨人/法师（M10 修订，实测驱动）。** M6.4 实测敌方峰值金币 280（pop 8 时代）买不起 400 金巨人；M10 在 popCap 12 下重测，峰值**反而只有 150**（AI 更快把钱花进 buildOrder 轮转）——「敌方会用新单位」必须先强化经济。扫描 `startGold × startMiners`（buildOrder 同步加 giant+mage，5 种子）：

| 格子 | 时长 | 敌方造出巨人？ |
|---|---|---|
| 300/4 | 158s | 否（轮转的钱全花在矿工） |
| **300/5** | **192s** | **是（giant×1，训练台账实测）** |
| 400/4 | 184s | 否 |
| 450/3 | 196s | 是 |
| 260/4 · 260/5 | 157s · 192s | 否 |

选 **300/5**：能实际造出巨人的最温和强化。**再次验证 M4b 教训**：给敌方加钱会让对局**更短**（280 → 192s，双方都变富、玩家 12 人口军队更早成型）。`nextBuildType`「买不起卡死」缺口**未被触发**（训练台账探针证实每个买得起的格子都实际造出了巨人）——Q2-B「用数据绕开而非修 sim」成立，缺口继续留在文档。新增**构成断言**：`level-3-winnable.test.ts` 用训练台账（真实决策路径重放）断言敌方训练命令含 `giant ≥ 1`——防 M6.4 式「改了 buildOrder 但什么都没发生」的静默空转。

**实测时长（最终发布配置，5 个种子完全一致）：192 秒 = 3.2 分钟**，结束方式为敌方基地 3000→0（时长偏窗口下缘：敌方变强反而更快分出胜负，接受）。

#### 8.4.5 关卡注册表

`data/levels.ts` 导出 `LEVELS: readonly MatchConfig[]`，**数组顺序即关卡顺序**。不在 `MatchConfig` 上加 `order` 字段 —— 数组顺序已经表达了它，多一个字段就有两个真相来源。关卡名走 i18n 键 `level.<levelId>.name`，映射放文案层（§7.5）。

#### 8.4.6 关卡选择菜单（M7 修订）

新增 `render/scenes/MenuScene.ts`（薄渲染器）+ `render/menu/layout.ts`（Phaser-free 纯函数，配测试），作为启动后的第一个界面（`BootScene` → `Menu` → `Battle`）。

- **入口与解锁**：解锁状态读存档的 `furthestLevel`（与 BootScene 原恢复逻辑同一字段、同一规则：`furthestLevel >= index` 即解锁），菜单永远不可能提供恢复流程到不了的关卡。无尽行只在打完最后一个战役关后解锁。
- **列表项**：`LEVELS` 数组顺序 = 菜单行顺序，标签取 `level.<levelId>.name`。未解锁行灰显、不可点。**M8 修订**：每行下方显示一行**机制说明**（`level.<levelId>.desc`）——说明玩家**在游戏里看不见的机制**（关卡 1 敌方无经济 = 场上没有敌方矿工，曾被人误读为 bug；无尽「只能战败」同理）。机制必须被告知，而不是被猜出。
- **恢复语义不变**：`BootScene` 不再直接读存档选关，改由菜单承担；`resumeLevelIndex(furthestLevel)` 纯函数封顶在最后一个战役关（防止恢复停进不可通关的无尽）。
- **辅助操作**：菜单提供「重置进度」（有进度才显示，写回 `DEFAULT_SAVE`，走既有容错写路径）。**M7b 修订**：另提供「速度偏好」（点击循环 1x→2x→4x）与「音效 开/关」两个开关，并排置于关卡列表与重置按钮之间；两者均写入存档（`speedPreference` 既有字段 + 新增 `sfxMuted: boolean`，宽容合并不升版本）。速度偏好仅持久化（下一局开局生效，`BattleScene.create` 已有读取路径）；音效偏好与「暂停/结算强制静音」在调用点 OR 合并——`AudioManager` 的 muted 是瞬态门不是偏好，偏好只存于存档。
- **结果浮层**：新增第三个按钮「菜单」，`resultButtonRects` 从 2 键扩为 3 键（宽度重排），战役/无尽关都显示。

#### 8.4.7 训练进度显示（M7 修订）

HUD 资源面板下方新增**队首训练进度条**：`render/hud/training-progress.ts`（Phaser-free 纯函数，配测试）读 `world.trainingQueue[side][0]`（渲染层只读 sim，合规），给出「单位名 + 剩余秒数（m:ss）」与 0..1 完成度；`hud/index.ts` 把它画成填充条 + 标签。**队列空时整组隐藏**。只显示队首：队列是串行的，队首进度就是「下一个单位什么时候出现」的完整答案；完整队列列表会让已有 9 键的底栏更拥挤。

### 8.5 首版内容量

首版只做 **2 个关卡 + 无尽模式**。关卡 JSON/TS 格式一旦定好，加关卡是纯数据工作；2 关足够验证「数据驱动」这条路走得通。

## 9. AI、测试与迭代

### 9.1 两层 AI

| 层 | 频率 | 职责 |
|---|---|---|
| **战术层** | 每约 1 秒（30 tick）决策一次 | 「现在该造什么兵、要不要推进、要不要撤退」 |
| **单位层** | 每个逻辑 tick | 「找到最近的敌人并走过去打」这类局部规则 |

**关键设计：玩家与 AI 共用同一套战术层接口。** 玩家战术层的「大脑」是输入指令（`Command[]`），AI 战术层的「大脑」是脚本——AI 本质上是在**替玩家按按钮**。这带来两个好处：天然公平（AI 无法使用玩家没有的能力），以及极容易调难度（只改脚本的决策频率与贪心程度）。

战略层（资源分配、科技路线）不在 v1 范围内，因为 v1 无科技树。

### 9.2 测试策略

**范围：仅对纯逻辑核心写 Vitest 单测。渲染层不测。**

测试对象：兵种数值与伤害结算、资源产出、波次生成、状态机迁移、分离约束、目标锁定、胜负判定、**确定性回归**（相同种子 + 相同指令序列 → 相同世界状态哈希）。

不做端到端测试（Playwright）。原型期投入产出比太低，留到 UI 稳定之后。

### 9.3 平衡 harness（M2 交付物）

**接口**（`src/sim/harness.ts`，纯函数、无渲染、可在 Vitest 与将来的 Node CLI 中调用）：

```ts
interface Scenario {
  name: string;
  player: Partial<Record<UnitTypeId, number>>;
  enemy: Partial<Record<UnitTypeId, number>>;
  /** 同阵营单位之间的初始间距。用于构造「紧贴身后」与「孤零零」两种布局。 */
  spacing?: number;
  /** 是否生成基地。无基地的对撞场景靠 §6.6 的「单位归零判负」得出结果。 */
  withBases?: boolean;
}

interface ScenarioResult {
  name: string;
  winner: 'player' | 'enemy' | 'draw';
  ticks: number;
  survivors: Record<Side, number>;
  damageDealt: Record<Side, number>;
  hash: string;
}

function runScenario(scenario: Scenario, seed: number, maxTicks: number): ScenarioResult;
```

**对撞矩阵测试**（`src/sim/harness.test.ts`）跑一批**同价位**组合并用 `console.table` 打印。矩阵必须包含以下三类场景：

1. **同价位兵种对撞**：如 `剑士×10 vs 弓箭手×12`（1000 金 vs 960 金）。
2. **弓箭手带前排掩护** —— 验证 R1/R2 的**唯一**手段：`剑士×5 + 弓箭手×6 vs 剑士×10`，初始布局让弓箭手紧贴剑士身后。
3. **弓箭手无掩护** —— 反例对照：`弓箭手×10 vs 剑士×10`，弓箭手应大幅落败。

这是 §3.1（纯逻辑核心）+ §5.1（整数 tick 确定性）+ §9.2（Vitest）三条决策的最终兑现点。没有它，前面三条的投入只兑现了一半。有了它，调一次平衡的成本从「几分钟手动玩」降到「几百毫秒跑完 100 场」，且结果可复现、可对比。

**这也是 M2 必须先于 M3 的原因。**

## 10. 持久化与部署

### 10.1 持久化

仅用 `localStorage`，存：

- 关卡进度（已解锁关卡、各关是否通关）
- 设置（音量、语言、速度偏好）
- 无尽模式最高波次

**必须带版本号字段**（如 `stickWarSave.v1`），以便将来迁移。成本极低的未来保险。

#### 10.1.1 存档 schema（M5b 落定）

单一键 `stick-war-web:save`，值为 JSON：

```json
{
  "version": 1,
  "furthestLevel": 0,
  "endlessBestWave": 0,
  "speedPreference": 1
}
```

- `furthestLevel`：**最远到达的关卡下标**（即解锁进度 = 最远解锁），**仅在**玩家**赢**时推进（输了不推进）。
- `endlessBestWave`：历史最高波次（无尽模式第 N 波失败时取 `max`）。
- `speedPreference`：`1|2|4`，开新一局时作为初始速度。
- **读取必须容错**：键不存在 / JSON 损坏 / `version` 不符 → 静默回落默认值，**不崩溃**（try/catch 包整个读路径）。
- **写入**用 try/catch（隐私模式下 `localStorage` 可能抛异常）。
- **不存进行中的对局**（刷新即重开当前关，原文保留）；「恢复」= 从 `furthestLevel` 关卡重新开始。

### 10.2 部署

纯静态站点，部署到 **GitHub Pages + GitHub Actions**：推送 `main` 自动构建部署，免费，与仓库天然集成，无需第三方账号。

**必须配置** `vite.config.ts` 的 `base = '/stick-war-web/'`，否则 GitHub Pages 子路径下所有资源 404。

## 11. 里程碑

每个里程碑可独立验收，验收标准必须可客观判定（能跑 / 能打赢），不接受「感觉差不多了」。

### M1 — 骨架

**内容：** 项目脚手架（Phaser 4.2.1 + Vite + TS + Vitest）、ESLint 边界规则、`src/sim/` 空壳与类型定义、`data/constants.ts`、渲染层能画出地面线与一个静态火柴人、30Hz 逻辑帧 + 插值渲染管线跑通、种子 PRNG。

**验收：** 屏幕上有一个静止火柴人；逻辑 tick 计数器在跑；浏览器控制台能看到 `tick` 递增而渲染帧率独立；`npm test` 能跑通一个 PRNG 确定性测试。

### M2 — 移动与战斗

**内容：** 单位状态机、1D 排序-分离约束（§6.2）、目标选择与锁定（§6.4）、伤害与护甲结算（§6.5）、弹丸、死亡与移除（§6.6）、六步 tick 编排器（§6.1）、火柴人行走/攻击/死亡动画、平衡 harness（§9.3）。

**验收（三条硬指标，全部可客观判定）：**

1. **自动接战**：从初始间距 600px 出发，双方在 **≤ 400 tick**（约 13 秒）内产生首次伤害。
2. **能打完**：对局在 **≤ 6000 tick**（3.3 分钟）内出现明确胜负（`outcome !== 'ongoing'`），且**无单位重叠** —— 任意同阵营相邻单位的间距 ≥ 半径之和 − 0.5px 容差。
3. **可复现**：同一场景 + 同一种子跑两次，**状态哈希逐字节相同**。

> 验收**不**要求胜负结果符合 §6.5 的克制关系。那是数值平衡，是 harness 的**产出目标**而不是 M2 的**验收门槛**。M2 只需保证「机制正确、结果可复现」；数值好不好由 harness 报告，不混进验收标准。

> M2 的「结果可复现」验收项是 §3.1 + §5.1 + §6.1 的最终检验。

### M3 — 经济与指令

**内容：** 金矿、矿工采集循环、金币与人口 HUD、造兵队列、点击造兵、单位选中、姿态指令、全军推进/撤退、相机滚动与缩放、速度控制。

**验收（四条硬指标 + 肉眼项）：**

1. **经济闭环**：矿工自动往返，金币在 **600 tick 内 ≥ 220**（恰好完成 1 次往返）且 **800 tick 内 ≥ 240**（第 2 次在推进）。数字由数值推导：往返 190px×2 @ 70px/s + 采集 90 tick = 252 tick，600 tick 内完成 2 次余量不足。
2. **造兵闭环**：`train` 指令 → 金币扣除 → 队列推进 → 单位在 `trainTime` 后出现在基地附近，且人口计数正确；人口或金币不足时指令被拒绝且**金币不变**。
3. **指令闭环**：`setStance` 后单位的 `stance` 在**下一个 tick** 更新，且行为随之改变。
4. **批处理无关的确定性**：**相同的 tick 数**在 1x 与 4x 下产出相同状态哈希 —— 速度只改「每帧跑几个 tick」，不改 tick 本身。

   > **勘误（M3 实现期修正）**：本条原文写的是「同一对局在 1x 与 4x 下跑出的状态哈希相同」，这是**不可实现的**：跑 10 秒，4x 会比 1x 多跑 4 倍的 tick，状态本就应当不同 —— 断言它们相同等于断言速度控制不起作用。真正需要的不变量有两条：
   > 1. **批处理无关**：同样数量的 tick，无论被怎样分组进帧（30/45/60/120 fps），状态哈希相同。
   > 2. **指令只进一个 tick**：一帧内跑多个 tick 时，该帧收到的指令只能作用于**第一个** tick（否则 4x 下一次点击会花 4 倍金币）。
   >
   > 两条都已在 `src/render/speed-determinism.test.ts` 中实现，且经变异测试确认可以失败。

**必须肉眼确认**（spec 工作方式：验收必须实测）：

| # | 目视项 | 怎么确认 |
|---|---|---|
| 5 | 矿工真的在基地与矿点之间往返，金币在涨 | `npm run dev` 观察 |
| 6 | 点按钮能造兵，单位出现在基地旁且不重叠 | 点击四个兵种按钮 |
| 7 | 选中单位有脚下标记，姿态指令改变其行为 | 点单位 → 点「驻守」 |
| 8 | 相机能滚动与缩放，且不露出世界外的空白；**0.6x 时敌方基地可达** | A/D、鼠标贴边、滚轮 |
| 9 | 速度控制生效且不改变战果 | 1x 与 4x 各跑一局对比 |

第 4 条与第 9 条一起构成速度控制的完整验证 —— 单测能断言批处理无关，但「4x 下真的更快」只能肉眼判断。

> **勘误（M3 实现期修正）**：第 8 条原文只要求「不露出世界外的空白」。仅此不够：若相机钳制忽略了 Phaser 的 `originX = 0.5` 偏移，右边界会**小于** Phaser 自己的允许范围，于是相机停在离世界右缘 400px 处 —— 既没有露出空白，也**永远看不到敌方基地**。M3 已修正该钳制，并在 `camera.test.ts` 中断言「世界最右像素可达」。

### M4 — AI 与关卡

**内容：** 两层 AI（§9.1）、波次脚本系统、关卡 1 与关卡 2、胜负判定与结算界面。

**拆分（2026-09-29）：** M4 拆为 **M4a**（AI 与波次，可 headless 客观验收）与 **M4b**（关卡、胜负条件、结算界面，需肉眼验收）。理由：把「能在 sim 内客观判定」的部分与「需要人看」的部分分开，前者的每一项都能写成确定性断言，后者的验收标准也不同。

**M4a 验收（已交付，557 tests）：** 关卡 1 形状不再第 1 tick 秒胜；波次到点生成；战术层只产出玩家同款 `Command` 且只在决策 tick；脚本关卡敌方不跑战术层；**参考玩家能打赢关卡 1**（5 种子）**且被动玩家会输**；哈希覆盖新状态。

**M4b 验收：** 见 §13.7 Q15（10 条）。核心：弓箭手能削减基地 HP；`'base'` 条件下敌方单位归零不判胜、基地归零才判胜、玩家单位归零仍判负；**关卡 1 行为与 M4a 逐 tick 完全一致（哈希不变）**；参考玩家能打赢也能输掉关卡 2；§6.5 相克矩阵仍全体一致；肉眼确认结果浮层与关卡流转。

## 12. 风险清单

| # | 风险 | 影响 | 缓解措施 |
|---|---|---|---|
| 1 | 数值不平衡（矛兵对基地效率偏高） | 最优解单一，策略深度丧失 | **M4b 实测确认**：矛兵每金币对基地高效约 1.7×。基地成为真目标后已列入验收项（§13.7 Q9）：先按「矛兵是攻城单位」接受，**但必须实测确认不出现「纯矛兵严格占优」**，否则再削 |
| 1b | **弓箭手对基地零伤害**（M2 遗留缺陷） | 远程单位在攻城阶段完全无效 | **M4b 修复**（§8.3、§13.7 Q7），并补单测；修后需重跑 §6.5 相克矩阵 |
| 2 | Phaser 4 资料少于 v3 | 踩坑时缺少参考 | 程序化美术降低对素材教程的依赖；只依赖稳定的场景/容器/图形 API；官方 v3→v4 迁移指南 |
| 3 | 单位数增长导致帧率跌破 60fps | 帧率不足 | **M5 实测修正**：实测峰值同屏 **23~25** 单位（关卡 1 峰值 23、无尽代理 25），远低于原假设的 120 —— 120 只是「双方人口上限 60+60」的理论天花板。真实风险因此**低得多**，但仍需按实测负载验证（S3 已改写）。后备方案为启动时预烘焙纹理图集（§7.1） |
| 4 | 1D 分离约束产生推挤抖动或穿透 | 视觉混乱，单位重叠 | 约束完全可单测；位置钳制到 `[0, worldWidth]`；**排序比较器必须是全序**（`x` 相同时以 `unit.id` 决胜），不能依赖排序稳定性 |
| 5 | 确定性被浮点破坏 | 回放与批量模拟失效 | 计时器强制整数 tick（§5.1）；禁止非确定性 API；用世界状态哈希做回归断言 |
| 6 | 远程单位被己方单位「卡位」而无法输出 | 弓箭手完全不可用 | R1/R2 派生规则（§6.4）；M2 的对撞矩阵包含弓箭手带掩护的场景 |
| 7 | 缩放后单位过小导致不可读 | 0.6x 下无法辨识兵种 | 配色 + 武器形状 + **体型（视觉缩放）** 三重区分（`palette.ts` + `rig.ts` 的 `VISUAL_SCALE` / `WEAPON`）；0.6x 下限经过可读性验证。**M6.5 修订**：巨人在 `VISUAL_SCALE` 中放大至 1.5×、武器改为巨锤（shaft+head 双块），使「一眼很强」的体型通道真正生效；其余兵种保持 1.0×。体型是**渲染层专属通道**，不动 sim `bodyRadius` 与分离间距。 |
| 8 | 程序化音效质量不足 | 打击感打折 | 音效只做反馈不做表现；关键同步点已由 `windupTicksLeft` 保证；必要时可后续替换为素材 |

## 15. 未启用字段的登记

**这张表存在的理由：** 本项目已有**两次**「新增字段没进 `hashWorld`」的同类疏漏（M4a 的 `waves`/`aiProfile`、M4b 的 `endless`）。把未启用字段集中登记，是为了在**启用或删除它的那个提交**里就能看见这条义务。

| 字段 | 状态 | 处理 |
|---|---|---|
| `MatchConfig.difficultyMult` / `World.difficultyMult` | **死字段**：`createWorld` 从 config 拷到 `World`，但**无任何 system 读取**，也**不在 `hashWorld`** | **M5a 删除**（决定不用它：实测表明波次预算单独就足以产生不可避免的战败，乘算系数是多余的旋钮，见 §8.4.4）。删除同时避免了给 `Unit` 新增字段，也就避免了改 `hashWorld` 的 unit 行 |
| `World.nextWaveTick` | **残留字段**：`createWorld` 写一次，无人读；`advanceWaves` 直接从波次表读 `atTick` | **M5a 删除**（它是一份无人维护的波次时刻副本，留着只会误导） |
| `sim/rng.ts`（`nextRandom` / `randomInt`） | **从未被消费**：实测所有关卡对种子完全惰性，3 个种子逐字节相同 | **保留但不启用**。M5 的无尽波次用固定构成规则（§8.4.4），不需要随机。将来若启用，生成必须把新 `rngState` 写回 `world` 且结果必须进哈希 |

> **附带发现（M5a 实测）：** `world.rngState` **被哈希**（`hash.ts`）但**从未被消费**，所以**不同种子会产生不同的哈希、却完全相同的对局**。这不影响正确性（哈希的职责是「同样输入 → 同样输出」，而种子确实是输入之一），但它是**确定性守卫的一处噪声**：哈希在为一个对玩法毫无影响的值编码。若将来启用 PRNG，这条自动消失；若不启用，可考虑把 `rngState` 移出哈希 —— **但那时必须同时确认没有别的消费者**。

| Q4 | 无尽终局 | `winCondition: 'annihilation'`（默认），玩家侧「单位归零即负」**无条件保持**。**明确接受**敌方不攻击玩家基地（无尽目标是「撑多少波」）。不显示「下一关」 |
| Q5 | 战线指示器 | Phaser-free 的 `render/frontline/layout.ts`（直方图分桶 + 基地血条矩形）+ 薄渲染器。**必须测**：分桶是纯算术，正是「肉眼看着对、边界错一位」的东西 |
| Q6 | 部署 | 加 `.github/workflows/deploy.yml`（push `master` → build → Pages）。**需要 remote**；没有 remote 就**如实记为「未做」**，不假装完成 |
| Q7 | i18n 英文范围 | **只加 locale 概念与可切换，不写英文文案**（没有第二个语言的需求；`t()` 的插值才是真需求） |
| Q8 | 验收标准修订 | spec 原验收「线上可玩 + 第 12 波 ≥ 58fps」**不可验收**：①依赖 remote ②第 12 波预算 820 金约合 8 个单位，与「120 单位」矛盾。改为按**实测**表述 |
| Q9 | 预算 vs 乘算 | 同 Q3。并**删除 `difficultyMult` 死字段**（而非留着当陷阱） |
| Q10 | 波次构成 | **固定比例 + 随波号渐进引入新兵种**（前几波只有剑士，之后依次加弓箭手、矛兵）。不用纯随机加权 —— 那会让「第 N 波」不可复现，违反本项目核心纪律 |
| Q11 | PRNG | **不用**。`rngState` 至今从未被消费，固定构成已足够。「能不用随机就不用」符合确定性优先的取向 |
| Q12 | 性能验收 | S3 的「120 单位」改为**实测峰值负载（约 25 单位）下 ≥ 58fps**，并如实记录「120 是双方人口上限之和，是理论天花板、从未达到」 |
| Q13 | M5a/M5b 内容划分 | 见 §11 的 M5 小节 |
| Q14 | 音效范围 | 6 种全做（挥砍/命中/死亡/金币入账/造兵完成/基地受损），**只做反馈不做表现**；**首次用户输入前不创建 `AudioContext`**；**暂停与结算时不播放** |
| Q15 | localStorage | 关卡进度 + 设置 + 无尽最高波次，带版本号字段；**读取必须容错**（损坏/版本不符时静默回落，不崩溃）；**不存进行中的对局**（刷新即重开当前关） |
| Q16 | 无尽入口 | 作为 `LEVELS` 的**最后一项**，关卡 2 打完点「下一关」进入。结果浮层按钮**按关卡类型区分**：战役关 = 重玩 + 下一关（末关为返回第一关）；无尽关 = 重玩 + 返回第一关 |
| Q17 | 无尽显示什么 | HUD 显示**当前波次**（「第几波」就是它的分数）；结算显示**撑到第 N 波** + localStorage 里的历史最高波次。两者都走 `render/` 的纯函数分支，可单测 |
| Q18 | 实测发现：种子是惰性的 | `rngState` **从未被任何 system 消费**，所以所有关卡对种子逐字节相同。无尽波次生成本可成为第一个消费者，但决定不用（见 Q11） |
| Q19 | 实测发现：峰值单位数 | 关卡 1 峰值 **23**、无尽代理峰值 **25**。**120 从未被接近** —— 它是「双方人口上限 60+60」的理论上限，不是任何实测负载。S3 因此重写（见 Q12） |
| Q20 | spec 陈旧内容清理 | 发现 §15「未启用字段登记表」与 M4b 的 §14 修订**从未真正落盘**（M4b 的编辑丢失），本次补上；S6 的 5~8 分钟与 §8.4.3 的 243~252 秒也一并修正为实测值 |

### 13.9 M5b 决策记录（2026-10-12，表现层与基础设施）

> M5b 只含**可 headless 客观验收**的部分；音效与部署拆到 **M5c**（需外部条件/肉眼验收）。全部「按推荐」确认。

| Q | 主题 | 决定 |
|---|---|---|
| Q1 | M5b/M5c 拆分 | **M5b** = 战线指示器 + 无尽适配 + i18n locale + localStorage（均可 headless 验收）；**M5c** = 音效 + 部署（音效需首次输入/暂停等交互验证，部署依赖用户 git remote） |
| Q2 | 音效驱动方式（M5c 落定） | 用**渲染层状态差分**（对比上一帧 sim 状态决定播什么），**不**在 sim 里加事件列表——加事件会进 `hashWorld`，徒增确定性风险。先例：`syncStickmen` 的 id 差分驱动死亡残影 |
| Q3 | 战线指示器结构 | `render/frontline/{layout.ts,index.ts}`（纯函数 + 薄渲染器，与 hud/result 同形）。**同时必须扩展 `handleClick` 守卫**：当前只保留左右各 240px，顶部中央会被点击穿透 |
| Q4 | 存档恢复语义 | 「恢复」= 从**最远到达关卡**重新开始（进度 = 最远解锁）；**不存进行中对局**；无尽最高波次存同一份存档 |
| Q5 | i18n 最小范围 | 加 `LOCALES` 注册表 + `setLocale()`；**修**姿态按钮 `label0` 缓存缺陷（`sync` 不刷新）；**补** `level.endless.name`；**不写英文**；不做设置 UI |
| Q6 | 部署（M5c） | 需用户提供 git remote；没有就**如实记为「未做」**，不假装完成；`deploy.yml` 可选 |
| Q7 | 性能验收 | FPS 追加到既有 tick 标签，**仅 dev 显示**（`import.meta.env.DEV`）；验收用外部 Playwright 实测 |
| Q8 | 直方图口径 | **只统计战斗单位**（矿工会在基地/矿点形成静态凸起，淹没有意义信号），**24 桶**（约 125px/桶） |
| Q9 | 无尽显示 | HUD 仅在无尽关卡显示**当前波次**（`waveIndex`）；结算副标题追加「无尽模式 · 用时 · 波次 N · 最高 M」；「下一关」按钮无需改（无尽是 `LEVELS` 末项 → 「返回第一关」）；新增键 `ui.wave` / `result.best` |
| Q10 | 存档 schema | 单一键 `stick-war-web:save` = `{version:1, furthestLevel, endlessBestWave, speedPreference}`；**读取容错**（损坏/版本不符静默回落）+ try/catch 写入；`speedPreference` 存偏好；`furthestLevel` **仅在赢时推进** |
| Q11 | FPS 显示 | 仅在 `import.meta.env.DEV` 下显示（生产不显示） |
| Q12 | i18n 最终清单 | `LOCALES` + `setLocale`；修 `label0` 缓存；补 `level.endless.name`；加 `ui.wave` / `result.best`；**加测试**覆盖所有 `LEVELS` 关卡 id 的 `level.*.name` 键存在 + locale 切换测试 |

> 确定性注意：本批次改动全部落在 `render/`、`i18n/`、`input/` 与 localStorage，**不触碰 `src/sim/`**，故无 `hashWorld` 风险。音效（M5c）若走渲染层差分同样不入 sim。
